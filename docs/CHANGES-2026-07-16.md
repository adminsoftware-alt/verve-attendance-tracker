# Changes — July 16, 2026 (full day)

Everything changed in the Verve attendance tracker today, in simple language, with
**before vs after** for each item. Commits: `5000ea5`, `1792a92`, `8cd054b`, `60ebd16`,
`7c2b9d2`, `5ee933c`, `224bc70`.

---

## 1. Bot-off days are no longer blank (webhook fallback)

**Before:** The report builder had a rule: *"no bot data + entered a breakout room =
zero hours."* When the Scout Bot was off all day (July 15), everyone hit that rule,
so the whole day showed blank in Team View — even though Zoom's webhook events were
all safely stored in BigQuery.

**After:** Bot data stays the primary source (unchanged when it exists). When it
doesn't, the person's full day is rebuilt from webhook events: Main Room from meeting
join → breakout room X while inside it → Main Room again → until they left. Real room
names are used when calibration ran that day; otherwise `Room-xxxxxxxx` (hours still
count). Estimated data carries a lower confidence score (0.35–0.5) for auditing.

**Result:** July 15 went from blank to **164 people / ~915 hours** recovered.
Files: `zt_intervals.py` (`build_presence_intervals` Step 5).

---

## 2. Mid-day bot crashes no longer mislabel the afternoon

**Before:** If the bot ran in the morning and died at 2 PM, everyone's afternoon was
blindly labeled "Main Room" — even people who were in breakout rooms.

**After:** The uncovered stretch of the day is tiled from the webhook timeline —
Main Room where webhooks say Main, the actual breakout room where they don't. The
code even determines which room a person was already in at the moment the bot died.

Files: `zt_intervals.py` (shared room-tiling state machine, Step 4).

---

## 3. One source of hours — migration finished

**Before:** Five endpoints still computed hours from raw bot snapshots with their own
math, so a downloaded CSV could show different numbers than Team View on screen:
- `/teams/<id>/report/monthly` (+ Employee Report Card CSV, Team Summary CSV)
- `/teams/compare` (Team Compare page; its avg-break was hardcoded to 0)
- `/employees/<id>/attendance/<date>` (+ CSV)
- `/employees/<id>/report/yearly`
- `/employees/classified-monthly` (visitors/vendors)

**After:** All five read `presence_intervals` — the same table Day View and Team View
use. Disagreement between screen and export is now structurally impossible.
Deliberately NOT migrated: the live grid and heatmap (position maps, not hours) and
the unrecognized-participants tools (they need raw names by design).

---

## 4. Background jobs own data freshness

**Before:** Opening a page could trigger a ~20-second rebuild (slow pages); "today"
refreshed hourly at best; a day whose data arrived late could stay frozen forever.

**After:** Three Cloud Scheduler jobs (region `asia-east1`), created via the app's
own service account:
- `intervals-rebuild-today-2min` — today rebuilt **every 2 minutes**, 8:00–23:59 IST
- `intervals-auto-build-sweep` — every 15 min, self-heals any of the last 35 days
  (missing, stale, or late-arriving data)
- `reconcile-zoom-nightly` — daily 9:00 AST IST (see #5)

Page-triggered builds can be fully disabled later with `PAGELOAD_AUTO_BUILD=false`
(harmless to leave on — with the 2-min job, pages never find anything stale).
New endpoint: `POST /intervals/auto-build`.

---

## 5. Nightly cross-check against Zoom's own records

**Before:** A calculation bug could hide for weeks until a human noticed a weird number.

**After:** New `GET/POST /reconcile/zoom` compares every person's daily total in our
system against Zoom's official Reports API and flags anyone off by more than 10%
(configurable), plus people present in only one source. Scheduled daily at 9 AM IST.
Any future bug becomes a flagged name the next morning instead of a silent error.

---

## 6. Webhook security holes closed

**Before:**
- Anyone who found the webhook URL could inject fake attendance events by simply
  omitting the signature headers (validation was skipped when headers were missing).
- The URL-validation handshake answered unsigned requests — usable as an "HMAC
  oracle" to forge valid signatures for arbitrary fake events.

**After:** Every webhook request — including `endpoint.url_validation` — must carry a
valid Zoom HMAC signature or it is rejected with 401. Zoom signs all of these, so
nothing legitimate breaks.

---

## 7. Login now actually protects the system

**Before:** All create/edit/delete endpoints were open to the internet with no auth.
A default password list (plaintext) was shipped inside the browser JS bundle.
`/chat` trusted whatever role the browser claimed. Duplicate usernames were possible.

**After:**
- `/auth/login` issues a signed 12-hour token (HMAC, stateless — works across all
  Cloud Run instances).
- **45 mutating endpoints** require the token via `@require_auth`; user management,
  admin data editing, and debug/test endpoints require admin/superadmin roles.
- Admin data-browser GETs (`/admin/snapshots`, `/admin/events`) are superadmin-only.
- The frontend attaches the token to every request; the bundled `DEFAULT_USERS`
  password list was deleted; `/chat` takes user/role from the verified token.
- Duplicate usernames are rejected at creation (a duplicate would shadow the other
  at login).
- Deliberately left open (no login context exists): `/webhook` (Zoom-signed),
  `/monitor/snapshot` + `/calibration/*` (bot / Zoom SDK app), scheduler-called
  builders, and `/admin/ops/partition-events` (temporary — delete after the swap).

**Action required:** everyone must log out and back in ONCE after this deploy.

## 8. People identified by email, not display name

**Before:** Identity = display name. Renames ("Shashank C" ↔ "Shashank Channawar"),
rejoin suffixes ("-1"), and name drift split one person into two rows, or made their
hours vanish from Team View.

**After:** Whenever a name maps to exactly ONE email that day (from snapshots or
webhooks), the email becomes the identity key — all name variants merge into a single
person with a single correct total. People with no email keep name-matching exactly
as before. Every consumer matches rows by BOTH name and email columns, so old
(name-keyed) and new (email-keyed) data coexist safely.

Files: `zt_intervals.py` (Step 1b identity map + `_remap`).

---

## 9. Estimated data is visibly marked (⚠)

**Before:** Hours guessed from webhooks looked identical to solid bot-measured hours.

**After:** Any person-day where more than half the time came from low-confidence
sources shows an orange **⚠** with a tooltip ("Estimated from webhook data") in the
Hours Pivot and both Team View tables. The flag survives rejoin-variant merges.
Backend: `estimated` field in `team_attendance_v2`, `range_v2`, `monthly_v2`.
Frontend: `MonthlyPivotTables.jsx`, `TeamView.jsx`.

---

## 10. Passwords are hashed (bcrypt)

**Before:** `app_users` stored plaintext passwords; login compared them in SQL.

**After:** New users are bcrypt-hashed at creation. Existing plaintext rows upgrade
automatically and silently on each user's next successful login (no manual migration,
no downtime). Wrong passwords are still rejected in constant time.

---

## 11. Bot detection is exact-match

**Before:** Substring matching — a real person whose display name merely contained
"Scout Bot" vanished from attendance tracking, and the calibrator could grab the
wrong participant to move through rooms.

**After:** Exact name match (after stripping Zoom rejoin suffixes like "-1") in both
the backend (`is_scout_bot`) and the calibrator app (`isBotNameMatch`).

## 12. Codebase cleanup + module split

**Before:** One 16,700-line `app.py`; six dead v1 endpoints with zero callers; an
admin add-snapshot route that had crashed on an undefined variable since the day it
was written; a broken chatbot date-lookup.

**After:**
- `app.py` is 13,200 lines; four new focused modules:
  - `zt_config.py` — env settings, BigQuery table names, shared BQ client
  - `zt_helpers.py` — IST time, name normalization, participant merge utils
  - `zt_zoom_api.py` — the Zoom REST client
  - `zt_intervals.py` — the entire presence-intervals subsystem
  Routes stay in `app.py`; behavior verified byte-identical by the test suites.
- ~2,000 lines of dead code deleted (v1 attendance/summary, team day/range,
  trends, with_leave, report/compare).
- `/admin/snapshots/add` fixed (undefined `IST` → `get_ist_now()`).
- Chatbot: internal override/leave actions now pass the caller's auth token;
  attendance-for-date points at the v2 endpoint.
- CORS now allows the `Authorization` header for the dashboard origin (without
  this, every dashboard call would have failed after login).

---

## 13. BigQuery cost work

**Before:** `participant_events` (webhook events, 630k rows) was unpartitioned —
every build scanned its entire history twice, forever-growing cost (~$10–15/month
and rising). Month-long snapshot scans (~1 GB) ran on every CSV export click.

**After:** Verified `room_snapshots_v2` and `presence_intervals` are date-partitioned
(one day ≈ 11 MB). A partitioned copy of `participant_events` was created; **the
swap runs automatically at 02:30 IST tonight** via a scheduled cloud agent (retries
at 03:15/04:00 if the streaming buffer hasn't drained). The expensive export queries
are gone. Net effect: the whole pipeline fits in BigQuery's free tier — ~zero added
cost, likely cheaper than before.

## Incidents during the day (transparency)

1. **~15-minute outage (~11 PM IST):** the module split shipped, but the Dockerfile
   copies Python files by name and didn't include the new `zt_*.py` files → workers
   crash-looped on import → 503 on everything. Fixed by adding the COPY lines
   (`5ee933c`). Zoom retries webhook deliveries, so no attendance data was lost.
   **Rule going forward: any new top-level .py file needs a Dockerfile COPY line.**
2. **BigQuery HAVING quirk (~30 min of failed 2-min builds):** `HAVING
   COUNT(DISTINCT email)` resolved `email` to the SELECT alias (an aggregate of an
   aggregate). Fixed by qualifying `pairs.email` (`60ebd16`). Builds self-healed.

Both were caught by monitoring within minutes and fixed the same hour. An
independent adversarial review of the full day's diff then found and fixed 8 more
issues (the CORS header being the critical one) before users were affected.
