System Overview

The Zoom Attendance Tracker calculates meeting attendance hours by processing two data sources:

Primary Source
Webhooks
Fallback Source
Bot Snapshots
Final Output
presence_intervals

Key principle: All hours displayed to users come from the presence_intervals table. This table is rebuilt every 2 minutes by a BigQuery JS-UDF state machine that processes raw webhook events.

Raw Data Tables

1. participant_events_p PRIMARY

Raw webhook events from Zoom. This is the source of truth for attendance tracking.

Column Type Description
event_date DATE Partition key. IST date when event was received (UTC timestamp converted to IST)
event_timestamp TIMESTAMP Exact UTC time of the event
event_type STRING One of: participant_joined, participant_left, meeting.participant_joined, meeting.participant_left, breakout_room_joined, breakout_room_left
meeting_id INT64 Zoom meeting ID (the recurring ID like 89757349012)
meeting_uuid STRING Unique instance ID for this specific meeting session
participant_name STRING Display name shown in Zoom (can change mid-meeting)
participant_email STRING Email if available (often NULL for external participants)
participant_id STRING Zoom's internal participant ID (changes on reconnect)
room_uuid STRING Breakout room UUID (for breakout events only)
room_name STRING Room name at event time (may be placeholder like "Room-abc123")

2. room_snapshots_v2 LEGACY

Bot-captured snapshots from Scout Bot polling every 30 seconds. Used for historical dates before webhook-primary cutover (2026-07-20).

Column Type Description
event_date DATE Partition key. IST date of the snapshot
snapshot_time TIMESTAMP Exact UTC time when bot captured this snapshot
room_name STRING Room name (includes prefix like "0.Main Room", "5.2:Team Name")
participant_name STRING Display name shown in Zoom at snapshot time
participant_email STRING Email if visible to bot
alone_in_room BOOLEAN Whether participant was alone in this room at snapshot time
meeting_id STRING Zoom meeting ID

3. room_mappings

Maps breakout room UUIDs to human-readable names. UUIDs rotate daily when rooms are recreated.

Column Type Description
mapping_date DATE IST date this mapping is valid for
room_uuid STRING Zoom's internal UUID for the breakout room
room_name STRING Human-readable room name (e.g., "5.2:Accurest-Meeting Room:Strategist")
mapped_at TIMESTAMP When this mapping was captured (newer = more accurate)
meeting_id STRING Meeting where this room exists
Why UUIDs rotate daily When breakout rooms are closed and reopened, Zoom assigns new UUIDs. The same room name "5.2:Sales Team" might have UUID "abc123" on Monday and "xyz789" on Tuesday. The room_mappings table captures these daily mappings.

Resolution rule: For each room UUID, compare the timestamp of the latest webhook event with a real name vs. the mapped_at timestamp in room_mappings. Whichever is newer wins.

CASE
  WHEN room_uuid IS NULL THEN event.room_name
  WHEN event_name IS NOT NULL AND mapping_name IS NOT NULL THEN
       IF(mapped_at > event_ts, mapping_name, event_name)
  WHEN event_name IS NOT NULL THEN event_name
  WHEN mapping_name IS NOT NULL THEN mapping_name
  ELSE event.room_name  -- fallback to placeholder
END

Presence Intervals (Final Table)

The presence_intervals table is the single source of truth for all attendance hours. It contains one row per person per room segment.

Column Type Description
interval_id STRING Unique UUID for this interval
event_date DATE Partition key. IST date this interval is attributed to (login-date rule)
meeting_id STRING Zoom meeting ID
meeting_uuid STRING Specific meeting instance
participant_key STRING Identity key: email when unambiguous, else normalized display name
participant_name STRING Display name (for UI display)
participant_email STRING Email if known
room_name STRING Room name (resolved via mapping logic)
room_category STRING main | breakout | break
start_ts TIMESTAMP When participant entered this room
end_ts TIMESTAMP When participant left this room
duration_seconds INT64 end_ts - start_ts in seconds
alone_seconds INT64 Seconds spent alone in room (bot data only)
snapshot_count INT64 Number of bot snapshots in this interval (0 for webhook-only)
source STRING webhook_fill (main room) | webhook_room (breakout)
confidence FLOAT64 0.5 (has leave event) | 0.35 (no leave event, capped)
built_at TIMESTAMP When this row was generated

State Machine Logic

The BigQuery JS-UDF processes events per participant and builds presence windows. Here's the step-by-step logic:

State Machine Flow
stateDiagram-v2
    [*] --> Outside: Initial state

    Outside --> InMeeting: participant_joined
    InMeeting --> Outside: participant_left
(if no rejoin after)
    InMeeting --> InMeeting: participant_left
(room transition, ignored)

    InMeeting --> InBreakout: breakout_room_joined
    InBreakout --> InMeeting: breakout_room_left
    InBreakout --> InBreakout: breakout_room_joined
(different room)

    InMeeting --> [*]: meeting ends
    InBreakout --> [*]: meeting ends
1

Sort Events by Timestamp

All events for a participant are sorted chronologically. Events span two partitions (D and D+1) to handle midnight-crossing meetings.

2

Build Presence Windows

Pair participant_joined → participant_left events. Each pair creates a "presence window" when the person was in the meeting.

3

Apply 5-Second Room Transition Rule

Zoom fires participant_left during room transitions. A participant_left within 5 seconds of a breakout_room_joined is ignored only if there's a participant_joined after it.

4

Coalesce Micro-Disconnects

If someone disconnects and rejoins within 30 seconds, merge into one continuous window (network glitch, not real exit).

5

Tile Window with Breakout Events

Within each presence window, use breakout_room_joined/breakout_room_left events to split time into room segments.

6

Apply Caps and Filters

Each segment is filtered by minimum duration (5s) and capped at maximum duration (10 hours for Main Room, 4 hours for no-leave segments).

Window Tiling Example

Presence Window: 09:00 ────────────────────────────────────── 17:00 (leave)

Events:
  09:00  participant_joined
  10:30  breakout_room_joined (Room A)
  12:00  breakout_room_left
  14:00  breakout_room_joined (Room B)
  16:00  breakout_room_left
  17:00  participant_left

Result Segments:
  ├─ 09:00 - 10:30  Main Room     (1.5 hr)
  ├─ 10:30 - 12:00  Room A        (1.5 hr)
  ├─ 12:00 - 14:00  Main Room     (2.0 hr)
  ├─ 14:00 - 16:00  Room B        (2.0 hr)
  └─ 16:00 - 17:00  Main Room     (1.0 hr)
                                  ────────
                    Total:         8.0 hr

Business Rules & Constants

Constant Value Purpose
TRANSITION_GRACE_MS 5,000 ms (5 sec) Window to detect room transitions. A participant_left within 5s of a breakout_room_joined is considered a room move, not a meeting exit — but only if there's a subsequent rejoin.
COALESCE_GAP_MS 30,000 ms (30 sec) Micro-disconnects under 30s are merged into continuous presence.
SEG_MIN_MS 5,000 ms (5 sec) Minimum segment duration. Shorter segments are dropped (filters Zoom's double-fire noise).
SEG_CAP_MS 600 minutes (10 hr) Maximum single segment. Prevents runaway intervals from missing leave events.
NO_LEAVE_CAP_MS 240 minutes (4 hr) Cap for segments without an explicit leave event (lower confidence).
IST_OFFSET_MINUTES 330 (5h 30m) Offset from UTC to IST for date attribution.
EARLY_CUTOFF 08:00 IST Events before 08:00 IST with no explicit join are considered yesterday's meeting tail (webhook-only edge case).
Login-Date Attribution Rule A session belongs ENTIRELY to the IST day the person logged in. If you join at 23:00 IST on July 22 and leave at 02:00 IST on July 23, all 3 hours count toward July 22. This matches Zoom's official daily report behavior.

Name Normalization

LOWER(
  REGEXP_REPLACE(
    REGEXP_REPLACE(
      REGEXP_REPLACE(name, r'\s*\([^)]*\)\s*', ''),  -- remove (parenthetical)
      r'\s+', ' '                                     -- collapse whitespace
    ),
    r'^\s+|\s+$', ''                                  -- trim
  )
)

Example: "Sayli Sonone (Verve)" → "sayli sonone"

Edge Cases & Fixes

1. 5-Second Rule Bug (Fixed 2026-07-23)

Problem A participant's real exit was ignored because it occurred within 5 seconds of a breakout room join, causing 10+ hours of phantom Main Room time.

Root cause: The original 5-second rule assumed any participant_left near a breakout_room_joined was a room transition. But if someone joins a breakout and then leaves the meeting entirely within 5 seconds, their exit was being filtered out.

Fix: Check if there's any participant_joined AFTER the participant_left. No rejoin = real exit, not a room transition.

function isRoomTransition(t) {
  // FIX: Only treat as transition if there's a rejoin AFTER this left
  var hasRejoinAfter = false;
  for (var j = 0; j < events.length; j++) {
    if (JOINS.indexOf(events[j].et) >= 0 && events[j].ts.getTime() > t) {
      hasRejoinAfter = true;
      break;
    }
  }
  if (!hasRejoinAfter) return false;  // no rejoin = real exit

  // ... rest of 5-second proximity check
}

2. Midnight-Crossing Meetings

Problem: Meetings that span midnight could attribute hours to the wrong day or create duplicate entries.

Fix: The builder reads TWO partitions (D and D+1) but only creates intervals for sessions that STARTED on day D. Sessions starting on D+1 are handled by tomorrow's build.

3. Zoom Double-Fire Events

Problem: Zoom sometimes sends identical events twice within milliseconds.

Fix: Events with identical (event_type, room, timestamp) within 5 seconds are deduplicated.

4. Room UUID Changes Mid-Day

Problem: If breakout rooms are recreated during a meeting, UUIDs change but names stay the same.

Fix: "Newest knowledge wins" resolution compares timestamps from both event stream and mapping table.

Appendix: SQL Queries

Calculate Total Hours for a Date

SELECT
  participant_name,
  participant_email,
  ROUND(SUM(duration_seconds) / 3600, 2) AS total_hours,
  COUNT(*) AS segments
FROM `breakout_room_calibrator.presence_intervals`
WHERE event_date = '2026-07-22'
GROUP BY participant_name, participant_email
ORDER BY total_hours DESC

Find Segments for a Specific Person

SELECT
  room_name,
  room_category,
  FORMAT_TIMESTAMP('%H:%M:%S', start_ts) AS start_time,
  FORMAT_TIMESTAMP('%H:%M:%S', end_ts) AS end_time,
  ROUND(duration_seconds / 60, 1) AS minutes,
  source,
  confidence
FROM `breakout_room_calibrator.presence_intervals`
WHERE event_date = '2026-07-22'
  AND LOWER(participant_name) LIKE '%sayli%'
ORDER BY start_ts
